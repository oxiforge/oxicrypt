# Integrating the oxicrypt C library

This guide is the contract between the oxicrypt C library and the program that loads it, for every language. The how-to for your language, `examples/<language>/README.md`, gets a first call of each kind right. This guide covers what the how-to relies on but does not state: what the module will and will not do, how long it lives, what each return code means, where randomness comes from, what to do with keys and shared secrets, how to ship the library, and what the `oxi` check does and does not prove. Every function named here is declared, with its full documentation, in [`oxicrypt.h`](../crates/oxicrypt-ffi/include/oxicrypt.h); where this guide and the header disagree, the header describes the library you hold. A statement marked **Open** has not yet been confirmed, and names the probe that settles it.

## What the library is and is not

The shared library in a release bundle (`liboxicrypt_ffi.so.<ABI>` on Linux, `liboxicrypt_ffi.<ABI>.dylib` on macOS, `oxicrypt_ffi.dll` on Windows, `liboxicrypt_ffi.so` on Android) is the cryptographic module: it is the image the module's integrity test verifies when it starts, so the program that loads it is never signed. The C interface code inside it lies outside the module's FIPS 140-3 boundary, as the header states in its first comment. `<ABI>` is the number `oxi_abi_version()` returns. It changes only when the interface breaks compatibility, never when functions are added, and it is independent of the release version. The ABI this guide describes is 4; its symbol list is [`crates/oxicrypt-ffi/abi/v4.txt`](../crates/oxicrypt-ffi/abi/v4.txt).

The module serves hashing (SHA-2, SHA-3), HMAC, AES (CBC, CTR, GCM, CCM, CMAC, KW, KWP), nine SP 800-90A DRBGs, HKDF and the TLS 1.3 key schedule, RSA, ECDSA, ECDH, finite-field DH, Ed25519, ML-KEM, ML-DSA, SLH-DSA, and LMS and XMSS verification.

`oxi_init(profile)` selects the algorithms the process may use, once. Profiles 1 and 2 follow the NSA's Commercial National Security Algorithm Suite (CNSA) 2.0 and 1.0:

| `profile` | Name | Algorithms | Supporting services |
|---|---|---|---|
| `0` | Unrestricted | every approved algorithm | every approved service |
| `1` | CNSA 2.0 | AES-256, SHA-384, SHA-512, ML-KEM-1024, ML-DSA-87, LMS and XMSS verification | HMAC-SHA-384 and -SHA-512, CMAC-AES-256, CTR_DRBG-AES-256, Hash_DRBG and HMAC_DRBG with SHA-384 or SHA-512, HKDF with SHA-384 or SHA-512 |
| `2` | CNSA 1.0 | AES-256, SHA-384, ECDH and ECDSA on P-384, RSA of at least 3072 bits, DH of at least 3072 bits | HMAC-SHA-384, CMAC-AES-256, CTR_DRBG-AES-256, Hash_DRBG-SHA-384, HMAC_DRBG-SHA-384, HKDF-SHA-384 |
| `3` | Migration | profiles 1 and 2 together; not a CNSA profile | as profiles 1 and 2 |

The TLS 1.3 key-schedule functions (`oxi_tls13_*`) are refused under profiles 1, 2 and 3. Any other `profile` value returns `OXI_RESULT_INVALID_INPUT` and initialises nothing. A service the profile does not admit returns `OXI_RESULT_ALGORITHM_RESTRICTED`, and so does a key generation or encapsulation handed a DRBG the profile does not admit. Under profile 1, HMAC_DRBG-SHA-256, the DRBG every how-to uses, is refused: use a CTR_DRBG-AES-256 handle (`oxi_ctr_drbg_aes256_new_rbg`), which the C integration case `test_pq_rbg_entry_points.c` drives through ML-DSA-87 and ML-KEM-1024 under profile 1, or HMAC_DRBG or Hash_DRBG with SHA-384 or SHA-512. SHA-256 itself is outside profiles 1 and 2, so the how-tos' hash step runs under profile 0 only. `oxi_active_profile()` reports the profile in effect.

What the library does not do:

- **No protocol.** There is no TLS, no handshake, no key confirmation and no session state. The TLS 1.3 key-schedule functions (`oxi_tls13_derive_secret_*`, `oxi_tls13_hkdf_expand_label_*`) derive secrets for a protocol you implement, under profile 0 only.
- **No certificates.** Nothing parses, builds or validates X.509, and nothing binds a public key to an identity.
- **No key storage.** Every post-quantum key and every seed is returned to your buffers, and keeping it is your program's job.
- **No key encoding.** Keys, signatures and ciphertexts are the raw byte strings FIPS 203 and FIPS 204 define. No PEM, DER, SubjectPublicKeyInfo or PKCS#8 form is produced or accepted.

## Process lifetime

**Initialise once per process, before any other call.** `oxi_init` runs the power-up sequence: the software integrity test over the library's own image, then the known-answer self-test of every algorithm the library links. Only when all pass does the module become operational. Before that, a service returns `OXI_RESULT_NOT_OPERATIONAL`, after any pointer checks its header comment places first: the ML-KEM and ML-DSA key generation, expansion and encapsulation functions check every pointer first, and the AES functions check their key handle and output pointers before the module state, as the buffer contract at the top of the header states, so a NULL there returns `OXI_RESULT_NULL_POINTER` instead. The `_new_rbg` constructors do not check the module state at all: they return only `0`, `OXI_RESULT_NULL_POINTER` or `OXI_RESULT_INTERNAL`, and the handle they build is refused at instantiation. The queries `oxi_abi_version`, `oxi_active_profile`, `oxi_is_operational`, `oxi_integrity_status` and `lama_manifest` (which returns the static, NUL-terminated manifest describing every `oxi_*` entry point, for tools that discover the interface from the loaded library) answer before initialisation and in any module state.

The first call's outcome is authoritative. A later `oxi_init` runs no test and returns that outcome: `0` if the first succeeded, `OXI_RESULT_NOT_OPERATIONAL` if it failed. A later call with a different profile still returns `0` and leaves the first profile active, so read `oxi_active_profile()` if you need to know. Call `oxi_init` from one thread before starting others. The implementation also lets concurrent first calls race safely: one call claims the self-test phase with an atomic compare-and-swap, and the others wait for its outcome and return it (`crates/oxicrypt-module/src/lib.rs`, `initialize_as` and `already_left_power_off`, exercised by that crate's unit tests, not by a C test).

**The cost of starting.** The algorithm self-tests that `oxi_init` runs took 181.80 ms, warm, on the reference machine of [`power-up-performance.md`](power-up-performance.md), most of it SLH-DSA, finite-field DH and RSA. The integrity test adds time that grows with the library's size. **Open:** the whole cost of `oxi_init`, integrity test included, for the release library. Probe: time `oxi_init(0)` in a fresh process against the extracted release library on each platform, over repeated runs. The first DRBG instantiation in a process adds the entropy source's start-up (see [Randomness](#randomness)). Pay both once, at start-up, not on a request path.

**If `oxi_init` fails, the module serves nothing for the life of the process.** `OXI_RESULT_SELF_TEST_FAILED` does not say which test failed or why. `oxi_integrity_status()` tells a corrupt image apart from one signed for another key, an unsigned build and an environment that could not read the image, and `oxi_integrity_status_detail` gives the cause in words. The remedies are in the header's table for `oxi_integrity_status`. The short form: if you received the library from anyone else, do not sign it, and obtain a fresh copy from its publisher. `oxi_integrity_key_fingerprint` writes the SHA-256 of the verifying key the library embeds. Compare it with the release key's fingerprint, recorded in the bundle's `BUILD-PROVENANCE.txt`, to know whose signature the library trusts.

**The error state.** A conditional self-test failure during operation, a key pair that fails its pairwise consistency test or an entropy source that fails while seeding, puts the module in its error state. The call that detects it returns `OXI_RESULT_CONDITIONAL_TEST_FAILED` or `OXI_RESULT_ENTROPY_UNAVAILABLE`, and every later call to a service, including `oxi_drbg_generate` on a handle already instantiated, returns `OXI_RESULT_NOT_OPERATIONAL`, after the same pointer checks. A key generation or encapsulation running in another thread when the module enters its error state zeroes the outputs it has already copied and returns `OXI_RESULT_NOT_OPERATIONAL`. Nothing but a process restart leaves the error state: report the failure, stop using the library, and let your supervisor restart the process, which runs the whole power-up sequence again. `oxi_is_operational()` returns `1` while the module serves and `0` otherwise.

**Fork.** A child process inherits a copy of every DRBG handle. The copy refuses `oxi_drbg_generate` and `oxi_drbg_reseed`, and key generation and encapsulation through it, with `OXI_RESULT_INVALID_INPUT` until the child re-instantiates it with `oxi_drbg_instantiate` or builds a new handle, so parent and child never draw the same output. The header's comment on `OxiDrbg` gives the full behaviour, including a process id reused after the parent exits, which is not detected.

**Threads.** What is tested, by the C integration case [`test_concurrent_services.c`](../crates/oxicrypt-ffi/tests/c-integration/test_concurrent_services.c), run in the `c-integration` job against a library built with fault injection:

- After one `oxi_init(0)`, one thread runs 1000 ML-KEM-512 key generations (`oxi_ml_kem_512_keygen_rbg` on its own HMAC_DRBG-SHA-256 handle, each pair checked by re-expanding its seed with `oxi_ml_kem_512_expand_key`) while a second thread computes `oxi_sha256("abc")` at least 1000 times during them. Every call returns `0` with the expected output, and the test asserts that the two threads' calls overlapped.
- While a test hook holds a DRBG handle as in use, a second thread's `oxi_ml_kem_512_keygen_rbg` and `oxi_ml_kem_512_encapsulate_rbg` on that handle each return `OXI_RESULT_BUSY` and write nothing, and once the hold is released the same calls return `0`.

That is the whole of what the test shows: two services at once in one process, and the busy refusal on one DRBG handle. It exercises no AES mode. What the implementation further guarantees, as documented in the header and not covered by that test:

- Calls on one `OxiDrbg` handle from several threads are safe: a call that finds the handle in use returns `OXI_RESULT_BUSY` and changes nothing. Retry after a pause, or give each thread its own handle, which avoids the contention.
- Any number of threads may use one AES key handle at once. Every AES function takes the handle shared, and the only state a call changes is the GCM or CCM invocation count, which is atomic.
- The typed DRBG handles (`OxiHmacDrbgSha256` and the like, taken by the classical key generation functions) have no busy flag. Serialise every call on one of them yourself.
- No handle may be freed while another thread uses it, and none may be freed twice. Either is undefined behaviour.

## Return codes

Every function that returns `int` returns an `OxiResult`: `0` is success and every other value is a distinct failure. Four functions return a value of their own instead: `oxi_abi_version` (the ABI number), `oxi_active_profile` (a profile code), `oxi_is_operational` (`1` or `0`) and `oxi_integrity_status` (the integrity indicator). The post-quantum, DRBG and AES functions write their outputs only on success, and when one with several outputs is refused after copying some of them, it zeroes those it copied. Their header comments list the codes they return, in the order they check for them. Other functions differ, and their header comments say how: the TLS 1.3 functions leave `out` zeroized after a late failure, `oxi_integrity_status_detail` writes `*written` on failure, and some comments, such as `oxi_sha256`'s, list no codes.

| Code | Name | Meaning | What the caller does |
|---|---|---|---|
| 0 | `OXI_RESULT_OK` | Success. | Use the outputs. |
| 1 | `OXI_RESULT_NOT_OPERATIONAL` | The module is not operational: `oxi_init` has not succeeded, or the module has entered its error state. | Before init, call `oxi_init`. After a failure, stop using the library and restart the process. |
| 2 | `OXI_RESULT_SELF_TEST_FAILED` | A power-up test failed during `oxi_init`. The module serves nothing until the process restarts. | Read `oxi_integrity_status` and `oxi_integrity_status_detail`, report them, and do not retry in this process. |
| 3 | `OXI_RESULT_CONDITIONAL_TEST_FAILED` | A conditional self-test failed during a call, such as a key pair's pairwise consistency test. The module has entered its error state. | Discard any output, stop using the library and restart the process. |
| 4 | `OXI_RESULT_ALREADY_INITIALIZED` | Reserved for a repeated initialisation. No function of this ABI returns it: a repeated `oxi_init` returns the first call's outcome (`crates/oxicrypt-ffi/src/lib.rs`, `oxi_init`). | None at this interface. |
| 5 | `OXI_RESULT_INVALID_INPUT` | An input was refused before any cryptographic result: a value outside its domain (a point not on the curve, an ML-KEM key that fails the FIPS 203 §7.2 or §7.3 check), an over-long signing context or personalization string, overlapping buffers, a range past the end of the address space, a key handle of another mode, an unknown `oxi_init` profile, or a DRBG handle inherited across `fork`. | Fix the input. For an inherited handle, re-instantiate it in the child. |
| 6 | `OXI_RESULT_ALGORITHM_RESTRICTED` | The active profile does not admit this service, or the DRBG passed to it. | Use an admitted algorithm or DRBG. The profile cannot change without a restart. |
| 7 | `OXI_RESULT_NOT_IMPLEMENTED` | A service the module names but does not implement. No function of this ABI returns it. | Treat as unavailable. |
| 8 | `OXI_RESULT_UNINSTANTIATED` | A DRBG handle was used before `oxi_drbg_instantiate` succeeded on it, or after an instantiation in a forked child failed. | Instantiate the handle. |
| 9 | `OXI_RESULT_RESEED_REQUIRED` | A DRBG passed its reseed interval and cannot reseed itself. No exported function returns it, because every C DRBG handle is seeded by the module and reseeds itself. | None at this interface. |
| 10 | `OXI_RESULT_NULL_POINTER` | A required pointer was NULL, or a NULL pointer came with a non-zero length. | Pass the buffer. |
| 11 | `OXI_RESULT_BUFFER_TOO_SMALL` | An output buffer is shorter than the documented minimum. Nothing is written. | Pass a buffer of the length the header states. `oxi_integrity_status_detail` reports the length it needs in `*written`. |
| 12 | `OXI_RESULT_OUTPUT_TOO_LONG` | A request asked for more output than allowed: above 65536 bytes from `oxi_drbg_generate`, or above 255 hash lengths from HKDF-Expand. | Ask for less, in several calls. |
| 20 | `OXI_RESULT_NOT_BLOCK_ALIGNED` | The input length is not a multiple of the AES block where the mode requires it. | Pad or split the input as the mode requires. |
| 21 | `OXI_RESULT_INVALID_IV_LENGTH` | The IV length does not match the mode. | Pass an IV of the mode's length. |
| 22 | `OXI_RESULT_TAG_MISMATCH` | A verification ran and failed: an AES-GCM or AES-CCM tag, a CMAC, an AES-KW or AES-KWP unwrap, or a signature. The AES functions write no output with it. | Reject the message or signature. Do not retry and do not use any output. |
| 23 | `OXI_RESULT_LENGTH_MISMATCH` | An input and output buffer pair have different lengths. | Pass matching lengths. |
| 24 | `OXI_RESULT_INVALID_NONCE_LENGTH` | The nonce length does not match the mode. | Pass a nonce of an allowed length. |
| 25 | `OXI_RESULT_INVALID_TAG_LENGTH` | The tag length does not match the mode. | Pass a tag of an allowed length. |
| 26 | `OXI_RESULT_INVALID_PAYLOAD_LENGTH` | The payload is longer than the mode allows. | Split the payload across messages. |
| 27 | `OXI_RESULT_INVALID_AAD_LENGTH` | The additional authenticated data is longer than the mode allows. | Shorten the AAD. |
| 28 | `OXI_RESULT_INTEGRITY_UNVERIFIED` | The module was initialised without its integrity test. `oxi_init` always runs the test, so the C interface does not return it. | Treat as `OXI_RESULT_SELF_TEST_FAILED`. |
| 29 | `OXI_RESULT_ENTROPY_INPUT_TOO_SHORT` | A DRBG was given entropy input below its minimum. The C interface takes no entropy input, so no exported function returns it. | None at this interface. |
| 30 | `OXI_RESULT_NONCE_TOO_SHORT` | A DRBG was given a nonce below the module's floor. The C interface takes no DRBG nonce, so no exported function returns it. | None at this interface. |
| 31 | `OXI_RESULT_RBG_TOO_WEAK` | The DRBG passed to a service is below the security strength the service requires. Nothing was drawn. | Pass a DRBG of sufficient strength (see [Randomness](#randomness)). |
| 32 | `OXI_RESULT_BUSY` | The DRBG handle is in use by another call, or the module's seed path (the single, process-wide source every DRBG draws its seeds from; see [Randomness](#randomness)) was held by another thread past its wait bound, a fixed 2^24 spin iterations. Nothing was changed. | Retry after a pause, or use one handle per thread. |
| 33 | `OXI_RESULT_ENTROPY_UNAVAILABLE` | The entropy source failed while seeding or testing. The module has entered its error state. | Stop using the library and restart the process. |
| 34 | `OXI_RESULT_KEY_EXHAUSTED` | An AES-GCM or AES-CCM key has reached the number of invocations its mode permits. Nothing was written and no IV was drawn. The key stays exhausted. | Establish a new key. |
| 255 | `OXI_RESULT_INTERNAL` | A case that should not happen, including an allocation failure in a constructor and an error this mapping does not name. | Report it. Treat the call as failed. |

**Invalid versus malformed.** Some calls tell an input that could not be decoded apart from one that decoded and failed verification. ECDSA verification returns `OXI_RESULT_INVALID_INPUT` for a public key or signature that does not decode and `OXI_RESULT_TAG_MISMATCH` for a well-formed signature that does not verify. Several calls make no such distinction: the SLH-DSA, LMS and XMSS verifications, and the two the how-tos use, which follow from the design of their standards:

- **ML-DSA verification** (`oxi_ml_dsa_NN_verify`) returns `OXI_RESULT_TAG_MISMATCH` for every signature that does not verify, a malformed one included, and for a context longer than 255 bytes. The interface takes the public key and signature at their fixed lengths, which FIPS 204 §3.6.2 requires a verifier to enforce, so no length error can arise inside the call. Within those lengths FIPS 204 verification has one outcome for every failure: Algorithm 3 returns false (FIPS 204 §5.3).
- **ML-KEM decapsulation** (`oxi_ml_kem_NNN_decapsulate`) returns `0` for a ciphertext that does not match the decapsulation key, with a pseudorandom shared secret derived from the ciphertext and `z`, the implicit-rejection seed stored in the decapsulation key. This is FIPS 203 implicit rejection (§6.3): the result reveals nothing about whether the ciphertext was altered. A program learns of a mismatch only when the two parties' secrets fail to agree, which is what key confirmation detects (see [From a shared secret to traffic keys](#from-a-shared-secret-to-traffic-keys)). Decapsulation does return `OXI_RESULT_INVALID_INPUT` for a decapsulation key that fails the FIPS 203 §7.3 hash check, and encapsulation for an encapsulation key that fails the §7.2 modulus check.

## Randomness

**The module seeds every DRBG itself, and a program supplies no entropy to a DRBG or to the ML-KEM and ML-DSA services.** There is no C function that takes an entropy input, a nonce or a seed for a DRBG. FIPS 140-3 Implementation Guidance (IG) 9.3.A sets out why. Under scenario 3(a), where the entropy source is inside the module's operational environment (its TOEPP, the tested operational environment's physical perimeter) and a component outside the module's boundary collects from it and loads the module, the module "cannot be validated": it "shall have direct access to the entropy source's GetEntropy() interface". Under scenario 2(b), entropy loaded from a source outside the TOEPP, the module can be validated only with the certificate caveat "No assurance of the minimum strength of generated SSPs (e.g., keys)". The module avoids both by reaching its entropy source directly.

**Three services take a caller's secret randomness.** Outside the DRBGs and the ML-KEM and ML-DSA services, three families take a secret value from the caller, and nothing is drawn inside the module:

- `oxi_slh_dsa_*_keygen(xi, pk, sk)` generates an SLH-DSA key pair from a seed the caller supplies.
- `oxi_ed25519_keygen(seed, pk)` derives the Ed25519 public key from a caller's 32-byte seed. The header says "nothing is drawn".
- `oxi_ecdsa_p256_sign_with_k` and `oxi_ecdsa_p384_sign_with_k` sign with a caller's per-message secret `k`, which must be uniformly random in `[1, n-1]`. The header says the interface "cannot enforce uniformity".

Each such input is a secret imported from outside the module: your program generates it, protects it as a private key, and is responsible for its quality. For ECDSA, the `oxi_ecdsa_p*_private_key_new_generate` and `_sign_sha*` handle functions draw from a DRBG instead.

**Constructing a handle.** Construct an `OxiDrbg` with one of the nine `_new_rbg` functions (`oxi_hmac_drbg_sha256_new_rbg`, `oxi_hmac_drbg_sha384_new_rbg`, `oxi_hmac_drbg_sha512_new_rbg`, the three `oxi_hash_drbg_*_new_rbg` and the three `oxi_ctr_drbg_aes*_new_rbg`), then call `oxi_drbg_instantiate(handle, perso, perso_len)`. Instantiation draws the entropy input and nonce from the module's seed path, the one process-wide source the module draws every DRBG's seeds from (the two kinds of seed path are below). Release the handle with `oxi_drbg_free`, which wipes the DRBG's state and then every byte of the handle. The personalization string is optional (NULL with length 0). It distinguishes this instance's output from other instances' and adds no entropy. Its limit is 720 bytes for HMAC_DRBG and Hash_DRBG and 144 for CTR_DRBG, and a longer one returns `OXI_RESULT_INVALID_INPUT` before any draw. `oxi_drbg_reseed` reseeds from the module's seed path on demand with optional additional input, and `oxi_drbg_generate` fills a buffer of up to 65536 bytes.

**Reseeding.** A handle reseeds itself from the module's seed path when it reaches its reseed interval, 2^48 requests: the HMAC_DRBG and Hash_DRBG `reseed_interval` of SP 800-90A Rev. 1 §10.1 Table 2, and the AES CTR_DRBG value of §10.2.1 Table 3. `OXI_RESULT_RESEED_REQUIRED` therefore never reaches a C caller. A reseed that cannot draw returns `OXI_RESULT_BUSY` or `OXI_RESULT_ENTROPY_UNAVAILABLE` from the call that triggered it.

**The two seed paths, and what an unassessed environment means.** On first use in a process, the module decides where its seeds come from:

- **The assessed path.** On an operational environment listed as assessed in the module's seed table, the seed comes from the module's own SP 800-90B jitter entropy source, which runs inside the boundary and is reached through its GetEntropy() interface (IG 9.3.A scenario 1(b)). The one assessed row is x86_64 Linux with the raw counter timer, claiming 1/2 bit of min-entropy per sample (`crates/oxicrypt-drbg/src/seed_table.rs`). That claim, and the entropy assurance that rests on it, apply to the specific machine the assessment measured.
- **The operating-system path.** On every other environment, including the macOS, Windows, Android and Linux aarch64 libraries a release ships, and on an x86_64 Linux machine whose timer fails the source's adequacy check, the module calls the operating system's generator itself (`getrandom` on Linux and Android, `getentropy` on macOS, `ProcessPrng` on Windows). The module runs there, but such an environment is an untested platform in the sense of IG 9.3.A Additional Comment 2: the assurance of the minimum strength of generated keys does not extend to it.

`oxi_entropy_on_demand_test(&label)` runs the seed path's on-demand test and sets `label` to the path it took. The `oxi selftest` command names the path too.

**First-use cost.** The first instantiation in a process builds and starts the entropy source when the assessed path is taken. Start-up runs the continuous health tests over 1024 consecutive samples, the minimum SP 800-90B §4.3 item 4 requires, and the module discards those samples, which that item permits. The start-up alone took 3.29 ms on the reference virtual machine of [`entropy-performance.md`](entropy-performance.md#start-up-health-test-time). Later instantiations in the same process do not repeat it. **Open:** the cost of the first instantiation in a fresh process on each release platform, the assessed x86_64 Linux machine included. Probe: `cargo bench -p oxicrypt-bench --bench drbg_first_instantiate` on each platform, a fresh process per sample, with the result recorded in `entropy-performance.md`.

**Strength.** Key generation and encapsulation compare the DRBG's security strength with the parameter set's requirement before drawing anything, and return `OXI_RESULT_RBG_TOO_WEAK` if it is lower. `oxi_drbg_strength_bits` reports a handle's strength.

| Parameter set | Required strength | Source |
|---|---|---|
| ML-KEM-512 | 128 bits | FIPS 203 §3.3 |
| ML-KEM-768 | 192 bits | FIPS 203 §3.3 |
| ML-KEM-1024 | 256 bits | FIPS 203 §3.3 |
| ML-DSA-44 | 192 bits | FIPS 204 §3.6.1 requires 128 and recommends 192, and below 192 reduces the claim to category 1. The module requires 192, so the claim is never reduced. |
| ML-DSA-65 | 192 bits | FIPS 204 §3.6.1 |
| ML-DSA-87 | 256 bits | FIPS 204 §3.6.1 |

So CTR_DRBG with AES-128 serves ML-KEM-512 only, AES-192 adds ML-KEM-768, ML-DSA-44 and ML-DSA-65, and the 256-bit parameter sets need a DRBG of 256 bits, such as HMAC_DRBG-SHA-256 or CTR_DRBG-AES-256.

**Key generation and encapsulation draw from the DRBG you pass, and never take a seed.** `oxi_ml_dsa_NN_keygen_rbg`, `oxi_ml_kem_NNN_keygen_rbg` and `oxi_ml_kem_NNN_encapsulate_rbg` take an `OxiDrbg` handle and draw their random inputs inside the module, as FIPS 203 §3.3 and FIPS 204 §6 require of the module: the 32-byte ML-DSA key-generation seed ξ, the two 32-byte ML-KEM key-generation seeds `d` (from which the key pair is expanded) and `z` (the implicit-rejection seed), and the 32-byte ML-KEM encapsulation randomness `m`. There is no interface that encapsulates with a caller's `m`.

**The stored-seed path.** If your design stores a seed instead of the expanded key, pass a `seed_out` buffer to key generation (32 bytes ξ for ML-DSA, 64 bytes `d` then `z` for ML-KEM) and later call `oxi_ml_dsa_NN_expand_key(seed, pk, sk)` or `oxi_ml_kem_NNN_expand_key(d, z, ek, dk)`, which reproduce the pair and run the pairwise consistency test on it. Pass NULL as `seed_out` and the module wipes the seed and returns only the pair. A stored seed computes the private key and must be protected as one (FIPS 204 §3.6.3, FIPS 203 §3.3). A seed that did not come from this module's key generation, whether from another library, a file you did not write or a test vector, is a private key imported into the module, and your program is responsible for how it was generated and protected.

**Testing interfaces.** The forms that take a caller's entropy (the SP 800-90A instantiate and reseed with an entropy input) and the derandomized internal forms of ML-KEM and ML-DSA (`keygen_internal`, `encaps_internal`, `decaps_internal`, `sign_internal`) exist only in the Rust crates, behind the default-off cargo feature `testing-interfaces`, which the test harness for NIST's Automated Cryptographic Validation Protocol (ACVP) vectors enables. The shipped library has none of them. The release workflow builds the library and the CLI in one invocation, `cargo build --release --target "$T" -p oxicrypt-ffi -p oxicrypt-cli` (the Linux legs run the same packages through `cargo zigbuild`), and the feature set of that pair includes neither `testing-interfaces` nor `fault-injection`. Check with `cargo tree -p oxicrypt-ffi -p oxicrypt-cli -e features`. The test hooks of the C integration suite, such as `oxi_test_hold_busy`, are declared in a separate header and exist only in a library built with `fault-injection` for those tests.

## Keys

**Generation and its self-test.** ML-DSA and ML-KEM key generation and key expansion run a pairwise consistency test on every pair before anything is written (FIPS 140-3 IG 10.3.A Additional Comment 1): ML-DSA signs a fixed message and verifies the signature with the new public key, ML-KEM encapsulates to the new encapsulation key and checks that decapsulation recovers the same secret. ECDH, ECDSA, Ed25519 and RSA key generation run their own. A failure returns `OXI_RESULT_CONDITIONAL_TEST_FAILED`, writes no key, and puts the module in its error state for the rest of the process (see [Process lifetime](#process-lifetime)). The test runs on expansion from a stored seed too.

**Sizes, in bytes.** Each buffer must be at least this long; the post-quantum functions take no length argument.

| Parameter set | Public or encapsulation key | Secret or decapsulation key | Signature or ciphertext | Seed |
|---|---|---|---|---|
| ML-DSA-44 | 1312 | 2560 | 2420 | 32 (ξ) |
| ML-DSA-65 | 1952 | 4032 | 3309 | 32 (ξ) |
| ML-DSA-87 | 2592 | 4896 | 4627 | 32 (ξ) |
| ML-KEM-512 | 800 | 1632 | 768 | 64 (`d` then `z`) |
| ML-KEM-768 | 1184 | 2400 | 1088 | 64 |
| ML-KEM-1024 | 1568 | 3168 | 1568 | 64 |

The ML-KEM shared secret is 32 bytes for every parameter set.

**Where key material lives.** Two models, depending on the service:

- **Held in an opaque handle for the handle's lifetime.** The AES mode keys, the ECDSA and RSA private-key handles (`oxi_ecdsa_*_private_key_*`, `oxi_rsa_*_private_key_*`), and the DRBG handles. Your program holds a pointer to the handle and must free each handle exactly once when it is done. An AES key enters its handle from your buffer: `oxi_aes_*_key_new` copies the raw key bytes in, the mode's `oxi_aes_*_key_free` zeroizes the handle's key schedule, and the buffer you passed stays yours to wipe as soon as `_key_new` returns. The ECDSA and RSA handles generate their keys inside the module from a DRBG.
- **Returned to the caller, nothing kept.** The post-quantum services. `oxi_ml_*_keygen_rbg` and `oxi_ml_*_expand_key` write the keys into your buffers, and sign, verify, encapsulate and decapsulate read them from your buffers on every call. With `seed_out` NULL, key generation wipes the seed it drew and returns only the pair. The buffers you pass, the secret key, the decapsulation key, the seed and the shared secret, are yours to wipe.

**Storage is the application's.** The library writes no file, keeps no key beyond the handles your program holds, and keeps no post-quantum key across calls. How a stored key or seed is protected (file permissions, an operating-system key store, a hardware module) is your program's decision and responsibility.

**Zeroizing.** In a language with deterministic memory release, wipe a secret with a store the compiler cannot remove as dead. In a garbage-collected language, keep secrets in memory the collector does not move or copy, and wipe that memory, because a moved object leaves a copy you cannot reach. Strings cannot be wiped in any of the managed languages below, so a secret formatted as text, such as the hex line the examples print, stays in memory until the runtime reuses it. Each example program wipes its secret key, decapsulation key and shared secrets this way before it exits, on success and on failure:

| Binding | Where the secrets live in the example | How it wipes them |
|---|---|---|
| C | static arrays | a loop storing zero through a `volatile` pointer, which the compiler may not remove |
| Python (`ctypes`) | `ctypes` buffers | `ctypes.memset(buffer, 0, len(buffer))` |
| Go (cgo) | byte slices passed to C | `clear(slice)`, and `clear` on each byte slice read from a file once copied |
| Node.js (`koffi`) | `Buffer.alloc` buffers | `buffer.fill(0)`, and the same on each buffer read from a file once copied |
| Java (Foreign Function & Memory API) | native `MemorySegment`s from an arena | `segment.fill((byte) 0)`, and `Arrays.fill` on any `byte[]` copy |
| C# (P/Invoke) | arrays from `GC.AllocateArray<byte>(n, pinned: true)`, pinned so the collector never moves them | `CryptographicOperations.ZeroMemory(array)` |

Freeing a DRBG handle with `oxi_drbg_free` wipes its state. **Open:** whether the Go, Node.js and Python runtimes ever move or copy the buffers the examples wipe, which the examples assume they do not. Probe: each runtime's documentation of its allocator for those types (Go heap objects, Node.js `Buffer` backing stores, `ctypes` buffers).

**Encodings.** The library produces and accepts only the raw byte strings of FIPS 203, FIPS 204 and the other algorithms' standards. An application that needs PEM, DER, SubjectPublicKeyInfo or PKCS#8 wraps and unwraps the raw bytes itself, or with an encoding library outside the module, and passes the module only the raw key. Unwrapping happens outside the boundary, so treat a private key decoded from a file as an imported key, as for a stored seed.

## From a shared secret to traffic keys

**The 32-byte shared secret is a 256-bit key.** FIPS 203 §3.3 states that, "Under appropriate conditions (see Sections 3.1 and 3.2, and SP 800-227)", the values returned by encapsulation and decapsulation "match (i.e., K′ = K) and can be used directly as a shared secret key for symmetric cryptography". Within those conditions, which are the open item below, the secret can serve directly as an AES-256 key when one key, with no context bound into it, is all the protocol needs.

**Derive when you need more keys or bound context.** FIPS 203 §3.3 requires that further keys "shall be derived from this 256-bit shared secret key in an approved manner, as specified in SP 800-108 and SP 800-56C". The C library exposes the SP 800-56C Rev. 2 §5 two-step (extract-then-expand) derivation as HKDF: `oxi_hkdf_sha256_extract`, `oxi_hkdf_sha384_extract`, `oxi_hkdf_sha512_extract` and the matching `_expand` functions. Their power-up self-tests use the NIST ACVP `KDA-HKDF-Sp800-56Cr2` vectors. A typical use: extract with a salt your protocol agrees on and the shared secret as input keying material, then expand once per key with `info` naming the key's purpose and binding the transcript (both parties' identities, the encapsulation key, the ciphertext). The SP 800-108 key-based key derivation function (KBKDF) is implemented in the Rust crate `oxicrypt-kdf` but has no C function. Under profile 1, use the SHA-384 or SHA-512 forms, and under profile 2 the SHA-384 form.

**Then encrypt with an AEAD the library exposes and confirm the key.** AES-GCM (`oxi_aes_gcm_key_new`, `oxi_aes_gcm_seal`, `oxi_aes_gcm_open`) draws each 96-bit IV from a DRBG handle you pass, the RBG-based construction of SP 800-38D §8.2.2, so your program never chooses an IV, and refuses a key that reaches 2^32 encryptions, the limit SP 800-38D §8.3 sets for that construction, with `OXI_RESULT_KEY_EXHAUSTED`. The AES key you pass to `oxi_aes_gcm_key_new` is a copy: wipe your buffer holding it once the handle exists. AES-CCM (`oxi_aes_ccm_*`) is also available. Because decapsulation never fails on a mismatched ciphertext, confirm the key before relying on it: each party proves it holds the same derived key, for example with a MAC over the transcript under a confirmation key derived for that purpose, and treats a failed confirmation as a failed key establishment.

SP 800-227 (Recommendations for Key-Encapsulation Mechanisms) binds a validated module: FIPS 140-3 IG D.S Additional Comment 4 states that "All approved KEMs shall comply with SP 800-227", and Additional Comment 6 states that its "shall" requirements RS1 to RS11 are tested by the validation laboratory, with RS9 the one that pertains to key confirmation. **Open:** what SP 800-227 itself says about key derivation and key confirmation after encapsulation, and the conditions FIPS 203 §3.3 defers to it for the two secrets to match. Probe: read SP 800-227's sections on key derivation and key confirmation, RS9 among them, and cite them here.

## Signatures

**Deterministic ML-DSA only.** `oxi_ml_dsa_NN_sign` is the deterministic variant of FIPS 204 §3.4: the same secret key, message and context give the same signature on every call. Any FIPS 204 verifier verifies it, because one verification algorithm serves both variants. FIPS 204 §3.4 warns that the deterministic variant makes side-channel and fault attacks harder to mitigate and "should not be used on platforms where side-channel attacks are a concern and where they cannot be otherwise mitigated". The hedged variant is not exposed through this ABI. SLH-DSA signing and Ed25519, ECDSA and RSA signatures are also available, and LMS and XMSS signatures can be verified.

**The context string.** Sign and verify take a context string of 0 to 255 bytes (FIPS 204 §5.2 and §5.3). A longer one makes `oxi_ml_dsa_NN_sign` return `OXI_RESULT_INVALID_INPUT` and `oxi_ml_dsa_NN_verify` return `OXI_RESULT_TAG_MISMATCH`. The empty context is the default. **Open:** the header's statement that X.509, CMS and the specifications of the IETF LAMPS (Limited Additional Mechanisms for PKIX and S/MIME) working group use the empty context. Probe: read the ML-DSA sections of the LAMPS RFCs for X.509 and CMS and cite them here. Use a non-empty context to separate signatures made for different purposes with one key, so a signature made for one cannot be presented as the other. The verifier must pass the context the signer used, or the signature does not verify.

**What a verifier checks beyond the signature.** A return of `0` from `oxi_ml_dsa_NN_verify` means this public key signed this message under this context. It does not mean the key belongs to whom you think. FIPS 204 §3.5 states that "Binding a public key to an identity requires proof of possession of the private key", and that in a PKI "issuing certificates involves assurances of identity and proof of possession". The library provides neither. Before trusting a signature, your program establishes that the public key is the expected signer's, through a certificate it validates, a pinned key or fingerprint, or a trusted channel. It checks that the message is the one the decision depends on, including any version, sequence number or expiry the protocol defines, so an old signed message cannot be replayed. And it checks that the context is the one this use expects. The interface takes keys and signatures at their FIPS 204 lengths, and every verification failure, a malformed signature included, returns `OXI_RESULT_TAG_MISMATCH` (see [Return codes](#return-codes)).

## Shipping

**Shared library or static archive.** Each library bundle holds the shared library, a static archive (`liboxicrypt_ffi.a`, or `oxicrypt_ffi.lib` on Windows, with the DLL's import library `oxicrypt_ffi.dll.lib` beside it), `oxicrypt.h`, the licences and `BUILD-PROVENANCE.txt`. Load the shared library unless you have a reason not to: it is the signed module and verifies its own image at `oxi_init`, so your program is never signed. A program that links the static archive carries the module inside itself. The archive ships unsigned, because an archive has no loadable image to verify, so the program you link it into must itself be integrity-signed. A module built from source with `OXICRYPT_INTEGRITY_VERIFY_KEY` set to a key pair of your own is signed with that pair, and [`integrity-signing.md`](integrity-signing.md) gives the commands, including the Apple and Windows signing orders. `BUILD-PROVENANCE.txt` gives signing commands for the release archive too, but they hold only if the open item below resolves in their favour. **Open:** whether a program linking the release bundle's prebuilt static archive, which embeds the project's verifying key, can be signed with your own key and pass the integrity test, or whether the archive must be built from source with `OXICRYPT_INTEGRITY_VERIFY_KEY` set to your key, as the repository README describes. Probe: link the release archive into a test program, sign it with a key pair of your own, call `oxi_init(0)` and read `oxi_integrity_status()`.

**Linux.** The library's `SONAME` is `liboxicrypt_ffi.so.<ABI>`. The bundle holds that file with `liboxicrypt_ffi.so` as a link to it: link with `-L<dir> -loxicrypt_ffi`, and the program asks the loader for the versioned name at run time. Tell the loader where to find it, by installing it on the system library path or by setting a run-time search path in your program, for example `-Wl,-rpath,<dir>`, which the release workflow uses to load the staged bundle. The library needs glibc 2.17 or later. **Open:** a relocatable search path relative to the executable (`-Wl,-rpath,'$ORIGIN/<dir>'`), which no release check exercises. Probe: link a program with it, move the program and library together, and run it.

**macOS.** The install name is `@rpath/liboxicrypt_ffi.<ABI>.dylib`, so the loader finds the library only through the program's rpath: link with `-Wl,-rpath,<dir>`, as the release workflow's load check does. Release dylibs carry an ad-hoc code signature only, because the project has no Apple signing identity. **Open:** an rpath relative to the executable (`@executable_path/...` or `@loader_path/...`), which no release check exercises. Probe: as for Linux.

**Windows.** `oxicrypt_ffi.dll` imports `vcruntime140.dll` from the Visual C++ Redistributable and the Universal C Runtime (`api-ms-win-crt-*`). Both must be installed on the target machine. The release check fails on any import not listed in [`scripts/release-imports/pe-windows-x86_64.txt`](../scripts/release-imports/pe-windows-x86_64.txt), so that list is the library's full set of run-time dependencies. Link a C program through `oxicrypt_ffi.dll.lib` and ship the DLL with it. The example programs load it by full path. Release DLLs carry no Authenticode signature, because the project has no Authenticode certificate.

**Android.** The library keeps the plain name `liboxicrypt_ffi.so`, with no ABI suffix, and is built for the `x86_64` and `arm64-v8a` ABIs and linked for 16 KiB pages. Package it in your app's native library directory for each ABI. In a Gradle build that is `src/main/jniLibs/<abi>/liboxicrypt_ffi.so`, and the app loads it like any other native library. **Open:** the `jniLibs` placement and loading inside an installed app, which the project does not exercise: its Android checks load the library from a directory on the device with a native test program built for API level 24. Probe: build an app with the library under `src/main/jniLibs/arm64-v8a/`, install it on an arm64-v8a device, and read `oxi_init(0)` and `oxi_integrity_status()` from it.

**Verifying provenance in a build pipeline.** Every bundle has a `.sha256` file beside it. In your pipeline:

1. Check the download: `sha256sum -c oxicrypt-ffi-<tag>-<platform>.tar.gz.sha256`.
2. Read `BUILD-PROVENANCE.txt` in the extracted bundle. It records the commit, the CI run that built the bundle, the key source, the integrity signature of the library and the fingerprint of the verifying key it embeds. A release-signed bundle says it was signed with the project's release key and gives its fingerprint. A bundle that says `NOT RELEASE-SIGNED` was signed with a key generated for one run, and does not show who built it.
3. Compare that fingerprint with the SHA-256 of the release verifying key in the repository, `keys/release-integrity-verify.pub`.
4. Verify the library offline: `oxicrypt-integrity-sign --verify <library>` reports `verify ok` and the fingerprint.
5. At run time, `oxi_integrity_key_fingerprint` in your program, or `oxi --integrity` from the CLI archive of the same release, reports the same fingerprint.

## Checking an integration

**The check.** Step 6 of each how-to checks the files the example program wrote against the `oxi` command-line tool from the CLI archive of the same release and platform, in both directions: `oxi` verifies the program's signature and decapsulates its ciphertext, and the program decapsulates `oxi`'s. The release check runs the same commands for each example, as `scripts/release-archive-check.sh crosscheck <cli-archive> <library-archive>`. The commands are in each how-to, their exit codes in [`oxi/README.md`](../oxi/README.md), and the expected program output in [`examples/README.md`](../examples/README.md).

**What it proves.** Your program's buffers, lengths, byte order and call sequence agree, on every byte of every key, signature and ciphertext, with an independent consumer of the same module, with no seed shared between them. A wrong buffer size, a truncated or misaligned key, a swapped argument or a lost byte shows up as a failed verification or as two different secrets. The one known answer from NIST at the end of step 6 (`oxi ml-dsa keygen 87 --seed` with an ACVP vector's seed, then the SHA-256 of the public key) ties `oxi` to the standard's own output for ML-DSA-87 key generation.

**What it does not prove.**

- `oxi` is built from the same source as the library, so a defect in the module's algorithms that both share passes the cross-check. Correctness against the standards rests on the module's known-answer self-tests and its ACVP vectors, not on this check, and the single NIST answer covers only ML-DSA-87 key generation from a seed.
- It exercises one parameter set of each algorithm (ML-DSA-87, ML-KEM-1024), under profile 0, from one thread, in one process. Your program's other parameter sets, its profile, its use of threads and handles, and its behaviour across `fork` are not checked.
- It does not check your error handling: what your program does with each return code, with the error state, or with a failed key confirmation.
- It does not check zeroizing, key storage, key encodings, how your program derives traffic keys from the shared secret, or how it binds public keys to identities.
- It does not measure randomness. Agreement between your program and `oxi` shows the bytes were passed correctly, not that the keys are unpredictable. That rests on the module's seed path (see [Randomness](#randomness)).
- It checks the bundle on the machine that ran it. It does not check how your shipped program finds and loads the library on your users' machines (see [Shipping](#shipping)).
