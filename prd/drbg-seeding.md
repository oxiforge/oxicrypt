# The module seeds its own DRBGs: the shared RBG interface and the seeding path

Status: draft, awaiting approval. Approval is the merge of this file and its acceptance criteria in `ISA.md` as a pull request carrying no feature code. This document is the specification of the change that both `prd/aes-gcm-iv-and-spec-update.md` and `prd/oxi-pq-and-how-tos.md` build on; it lands as its own code change before either of them. Standards cited are FIPS 140-3 Implementation Guidance (IG) as last updated November 20, 2026, SP 800-90A Rev. 1, SP 800-90B, SP 800-90C and ISO/IEC 19790:2012.

## Problem

Every DRBG the module offers is seeded by its caller. In Rust, `instantiate` takes the entropy input; at the C ABI, every `oxi_*_drbg_*_instantiate*` takes an entropy buffer. A program that reads its operating system's generator and hands the bytes to the module puts the module in the topology IG 9.3.A describes under scenario 3(a): the entropy source is inside the operational environment, a component outside the cryptographic boundary collects from it and loads the module, and such a module "cannot be validated". The module "shall have direct access to the entropy source's GetEntropy() interface" and "shall not rely on a component outside of the cryptographic boundary of the module, or on an operator of the module, to access the entropy source's GetEntropy() interface and obtain entropy data and deliver this entropy data to the module."

The module already contains an SP 800-90B entropy source, `oxicrypt-entropy`, assessed on one operational environment, and its Security Policy §9.3 states the intended design: the DRBGs "are designed to be seeded by this in-boundary entropy source via direct internal access (FIPS 140-3 IG 9.3.A scenario 1) [seeding-integration pending]". Nothing wires the two together, and two features now need randomness drawn inside the module: GCM IV generation and post-quantum key generation and encapsulation.

## Outcome

A program never supplies entropy. It constructs a DRBG through the module, the module seeds it from a source the module itself reaches, and every service that needs randomness takes that DRBG. On an operational environment the Security Policy lists as assessed, the seed comes from the in-boundary SP 800-90B source (IG 9.3.A scenario 1(b)). On any other environment the module itself calls the operating system's generator; that environment is an untested operational environment under IG 9.3.A Additional Comment 2, the module runs there, and the certificate's entropy assurance does not extend to it. The certificate's tested operational environments are exactly the assessed rows; every other release build, the Android, macOS and Windows libraries included, ships as a port to an untested environment, and the Security Policy lists the assessed environments, lists the ports as ports, and carries the Additional Comment 2 statement. Both AES and post-quantum features consume one trait in Rust and one handle in C, and nothing in the shipped library accepts caller entropy. SP 800-90C conformance is not claimed (IG D.T and D.U, transition ending May 20, 2028); the DRBGs remain SP 800-90A constructions, and entropy-source health-test failures are therefore conditional self-test failures that put the module in its error state (IG 10.3.A Resolution 7, as IG D.U GenRBG.5 footnote 6 states for a module that does not claim SP 800-90C).

### User stories

- A C developer calls `oxi_hmac_drbg_sha256_new_rbg`, `oxi_drbg_instantiate` with an optional personalization string, and passes the handle to `oxi_ml_dsa_87_keygen_rbg`. No entropy code exists in their program.
- A Rust developer writes `let mut rbg = HmacDrbgSha256::instantiate_from_module(b"my app")?;` and passes `&mut rbg` to `gcm_encrypt` and `ml_kem_1024::keygen`.
- A laboratory reviewer reads the Security Policy and finds, per operational environment, which seed path the module takes, the minimum entropy per request, and whether the environment is assessed or an Additional Comment 2 port.
- The CAVP DRBG tests, which supply `entropyInput`, still run, against a build with the testing feature on.

## Scope

### 1. The `Rbg` trait and its errors, in `oxicrypt-module`

```rust
pub trait Rbg {
    /// Fills `out` with no additional input. On error `out` is zeroized.
    /// A module-seeded instance reseeds itself from the module when its
    /// reseed counter reaches the SP 800-90A interval, so it never returns
    /// ReseedRequired; a testing-interface instance does.
    fn fill(&mut self, out: &mut [u8]) -> Result<(), RbgError>;
    /// SP 800-90A security strength the instance was instantiated at.
    fn strength_bits(&self) -> u32;
}

#[derive(Clone, Copy, Debug, PartialEq, Eq)]
pub enum RbgError {
    Uninstantiated,
    ReseedRequired,
    RequestTooLong,
    EntropyUnavailable,
    NotOperational,
    Busy,            // the pipeline lock's spin bound was exhausted
}
```

`Rbg` is not sealed: a Rust consumer could implement it over a fixed stream and hand that to `keygen` or `gcm_encrypt`. The validated module is the shared library and the `oxi` binary, where the only implementations are the nine DRBGs behind `DrbgKind`; a Rust crate consumer is outside that boundary, and the Security Policy states the boundary that way (the AES PRD's D2 says the same for GCM). The test-only `oxicrypt_drbg::testing::FixedStream`, compiled under `cfg(any(test, feature = "fault-injection"))`, is the one in-tree implementation other than the DRBGs and is what the algorithm crates' deterministic tests use: `FixedStream::new(bytes: &'static [u8], strength_bits: u32)`; `fill` serves the bytes in order and returns `RbgError::RequestTooLong` once they are exhausted, so a test that over-draws fails rather than wraps. Other crates' tests reach it through a dev-dependency `oxicrypt-drbg = { path = …, features = ["fault-injection"] }`, since `cfg(test)` does not cross crates.

`oxicrypt_module::Error` gains `Rbg(RbgError)` and `RbgTooWeak`. `RbgError` contains no `Error`, so neither type contains the other. `oxicrypt-drbg` maps `DrbgError` onto `RbgError` in one function, `rbg_error(e: DrbgError) -> RbgError`, with these arms and no wildcard: `Uninstantiated → Uninstantiated`; `ReseedRequired → ReseedRequired`; `RequestTooLong → RequestTooLong`; `Module(Error::Rbg(e)) → e`; `Module(_) → NotOperational`; `InputTooLong → RequestTooLong`; `InvalidSeedLength → RequestTooLong`; `EntropyInputTooShort → RequestTooLong` (the last three cannot arise from `fill`, which passes no input and whose seed path controls lengths; they map so the match is exhaustive and a new `DrbgError` variant fails to compile). `Display` for the new `Error` variants: `Rbg(e)` prints `random bit generator: <e>` with `e` printed as its variant name in words (`uninstantiated`, `reseed required`, `request too long`, `entropy unavailable`, `not operational`, `busy`); `RbgTooWeak` prints `random bit generator strength below the requirement`; `RbgError` implements `Display` with the same words on its own. `fill` on CTR_DRBG is `generate_df` with empty additional input. `strength_bits` returns 256 for every HMAC_DRBG and Hash_DRBG type, the only strength the crate instantiates (`hmac.rs:53`, `hash.rs:66`), and 128, 192 or 256 for CTR_DRBG by AES key size.

C mapping of the new Rust errors, in `oxicrypt-ffi/src/error.rs`: `Error::Rbg(Uninstantiated) → 8`, `Error::Rbg(ReseedRequired) → 9`, `Error::Rbg(RequestTooLong) → 12` (`OutputTooLong`), `Error::Rbg(EntropyUnavailable) → 33`, `Error::Rbg(NotOperational) → 1`, `Error::Rbg(Busy) → 32`, `Error::RbgTooWeak → 31`; the handle layer's own busy flag also returns `32`. The existing `DrbgError` mappings (`InputTooLong → 5`, `RequestTooLong → 12`, `error.rs:220`) are unchanged.

### 2. The seeding path, in `oxicrypt-drbg`

**Dependencies.** `oxicrypt-drbg` gains `oxicrypt-entropy` (features `raw-counter` on, `std` off; see section 4) and the new crate `oxicrypt-platform` (section 3). No cycle: `oxicrypt-entropy` depends on `oxicrypt-module`, `oxicrypt-sha`, `oxicrypt-zeroize` and, under `raw-counter`, `oxicrypt-timer`; `oxicrypt-platform` depends on `oxicrypt-module` only. The `dev-dependency` of `oxicrypt-entropy` on `oxicrypt-drbg` (`Cargo.toml:60`) stays, with `testing-interfaces` enabled on it, for the one pipeline-to-DRBG test (section 2, migration); the comment above it (`Cargo.toml:57`), which says `oxicrypt-drbg` does not depend on `oxicrypt-entropy`, is rewritten to say the dependency now runs the other way and the dev-dependency closes a cycle cargo permits.

**The seed source and the environment table.**

```rust
// oxicrypt-drbg/src/seed.rs
pub(crate) trait SeedSource {
    fn fill(&mut self, out: &mut [u8]) -> Result<(), RbgError>;
    fn name(&self) -> &'static str;          // "jitter source" | "operating-system generator"
}
pub(crate) struct AssessedJitter;             // uses the process-global pipeline (below)
pub(crate) struct OperatingSystem;            // oxicrypt_platform::os_random
pub(crate) enum SourceKind { Jitter }         // a further SP 800-90B source adds a variant and a SeedSource impl

// oxicrypt-drbg/src/seed_table.rs
pub(crate) struct EnvRow {
    pub arch: &'static str,                   // target_arch
    pub os: &'static str,                     // target_os
    pub timer: TimerSource,
    pub claimed_h: MinEntropy,                // never below MinEntropy::from_fraction_floor_const(1, 2)
    pub source: SourceKind,
    pub policy_ref: &'static str,             // the Security Policy §9.3 row id
}
pub(crate) const ROWS: &[EnvRow] = &[EnvRow { arch: "x86_64", os: "linux", timer: TimerSource::RawCounter, claimed_h: MinEntropy::from_fraction_floor_const(1, 2), source: SourceKind::Jitter, policy_ref: "OE-1" }];   // the row ships in this change: the environment the policy already assesses
#[derive(Clone, Copy, Debug, PartialEq, Eq)]
pub(crate) enum OsReason { NoRow, TimerInadequate }
#[derive(Clone, Copy, Debug)]
pub(crate) enum SeedChoice { Assessed(&'static EnvRow), Os(OsReason) }
pub(crate) struct SeedState { pub choice: SeedChoice, pub pipeline: Option<EntropyPipeline<JitterSource<'static, PlatformTimer>>> }
pub(crate) fn seed_path() -> Result<SeedState, RbgError>;   // called once per process, inside SEED's first critical section (below); on the assessed path it also constructs and starts the pipeline
pub(crate) fn get_entropy(out: &mut [u8]) -> Result<(), RbgError>;   // the one draw function both instantiate and reseed call; it calls SeedSource::fill on the implementation SeedState selects
pub struct SeedPathReport { pub path: &'static str, pub label: &'static str }   // path is "assessed" or "operating-system"; label as defined below
```

A row is keyed by architecture, operating system and timer source. The Security Policy's tested operational environments are specific machines; the certificate's assurance applies to those, and on any other machine of the same architecture the module takes the same path and the Additional Comment 2 statement applies, which the policy says in so many words. The table is data: an assessed environment is one row plus its policy entry. The smallest representable claim is H = 1/2 because the APT cutoff table's smallest non-binary row is H = 1/2 (`sp800_90b.rs:251`); a `const` assertion in `seed_table.rs` checks every row against that bound through `MinEntropy::from_fraction_floor_const(1, 2)`, a `const fn` twin this change adds to `oxicrypt-entropy` returning `MinEntropy` and panicking at compile time on an unrepresentable fraction (`from_fraction_floor` is not `const` and returns `Option`). `seed_path()` returns `SeedChoice::Assessed(row)` when the running target matches a row and `JitterSource::new(PlatformTimer::new(row.timer)?, operational_config(row.timer))` succeeds, which is where the timer-adequacy check runs (`jitter.rs:249`); the constructed source goes straight into the pipeline (below), so adequacy is measured once. It returns `SeedChoice::Os(OsReason::NoRow)` when no row matches, and `SeedChoice::Os(OsReason::TimerInadequate)` only on `TimerError::Inadequate { .. }`. Every other `TimerError` is not a selection: `Module(e)` returns `rbg_error`'s mapping of `e` and enters no error state (the caller was not admitted), and `Unsupported`, `Unavailable` and `Backwards` are entropy failures (below). The decision is made once per process on first use. An adequacy failure on a machine that matches an assessed row is a selection, not a failure: the adequacy check is what tells the assessed machine from a look-alike, so that machine is an untested environment and takes the operating-system path, and every report names it so. On the assessed machine itself a degraded timer is indistinguishable from a look-alike and takes the same path with the same label; that is accepted, since refusing to seed would deny service for a condition the operating-system path handles. The label every surface uses for the operating-system path is `operating-system generator (untested operational environment, IG 9.3.A AC2)`, with `; timer adequacy not met` appended when that was the reason; the label for the assessed path is `jitter source, assessed row <policy_ref>`. The assessed label names the row the machine matched, not a certification of that machine; the policy's Additional Comment 2 statement covers a machine that matches a row without being the tested machine.

**The process-global pipeline.** `oxicrypt-module` and `oxicrypt-drbg` are `#![forbid(unsafe_code)]`, and a global holding a pipeline needs interior mutability and `Sync`, so the cell lives in `oxicrypt-platform` (section 3) as `SpinCell<T>`: an `UnsafeCell<Option<T>>` behind an `AtomicBool` lock with `Acquire`/`Release` ordering, `lock()` spinning with `core::hint::spin_loop` for at most 2^24 iterations and then returning `Err(Busy)` (an iteration bound, not a time; the bench of section 7 records how long 2^24 iterations take on each platform beside the longest observed draw, and the bound is raised if it is not at least sixteen times that draw), an RAII guard that releases on drop, and a recorded process id. `oxicrypt-drbg` holds one `static SEED: SpinCell<SeedState>`; the choice and, on the assessed path, the pipeline are made in one critical section on first use, so there is one lock and no lock order. `SpinCell::lock` first reads the recorded process id and compares it with `oxicrypt_platform::process_id()`; on a mismatch it attempts a compare-and-swap of the recorded id from the old value to the sentinel `RESETTING = u64::MAX`; the thread that wins the swap resets the cell (drops the parent's contents without running their destructors, since they belong to another process's memory image, and clears the lock flag), then stores the current id with `Release`. Every other thread that reads the old id or the sentinel spins until it reads the current id, counting toward its spin bound, and only then contends for the lock, so no thread holds the cell while it is reset. The id is recorded as 0 at `SpinCell::new`, and the first `lock` in a process takes the same reset path from 0 with nothing to drop. A descendant that reuses a parent's process id after the parent exited is not detected by this check; the header and the guide state it, and `MADV_WIPEONFORK` or an `atfork` hook are recorded as the stronger choice for a later change.

Construction, inside that first critical section when a row matches, by `seed_path()`: `JitterSource::new(PlatformTimer::new(row.timer)?, operational_config(row.timer))` where `operational_config` builds a `JitterConfig<'static>` with `AdequacyConfig::default()`, `timer_source: Some(row.timer)` and the three identity strings `"operational"`; then `EntropyPipeline::new(source, row.claimed_h, Alpha::DEFAULT)` and `run_startup()` (1024 health-tested samples, discarded; the timer check). `TimerError` and `EntropyError` from construction or startup are both entropy failures (below). Each `get_entropy(out)` takes `conditioned_block()` 32 bytes at a time (each block carries h_in ≥ n_out + 64 bits, the full-entropy margin of IG D.K Resolution 19, as the policy §9.3 item 2 states) and zeroizes the unused tail of the last block. The critical section is the whole draw, which on this path is long (startup plus up to 1280 jitter samples); callers are instantiate and reseed only, which is why the spin bound is generous and `Busy` is the overflow result. Callers arriving during first use wait for the draws ahead of them in turn, so the bound is sized for the longest draw times sixteen concurrent instantiators (the count ISC-234 drives), and the header says `32` means retry after a pause, not a broken handle.

**Entropy failure is a module failure.** Any `TimerError` or `EntropyError` from construction, startup, a block or the on-demand test, and any `OsRandomError` from the operating-system path, calls `oxicrypt_module::enter_error_state("entropy source")` and returns `RbgError::EntropyUnavailable`. The error state is terminal and output-inhibiting (ISO/IEC 19790 §7.3.3, §7.10.1; AS10.09): every service, including `generate` on an already-instantiated DRBG, returns `NotOperational` from the next call: today a `generate` reaches the module gate only through the SHA primitive inside `H::mac` (`hmac.rs:381`); this change puts an explicit `require_operational()` at the top of every `generate`, ahead of the instance's own checks, so it is the first thing a call meets. A service already running when another thread enters the error state re-reads the module state word immediately before writing any output (the pattern the AES PRD's G19 uses for block methods) and, on a change, zeroizes its results and returns `NotOperational` instead of writing. The mechanism is one function, `oxicrypt_module::require_operational_for_output() -> Result<(), Error>`, a fresh read of the state word; in `oxicrypt-ffi` one helper, `pub(crate) fn write_out(dst: *mut u8, src: &[u8]) -> Result<(), OxiResult>`, calls it and then copies, and every copy into a caller buffer in that crate goes through `write_out`, enforced by a unit test that scans the crate's `src/*.rs` for `copy_nonoverlapping`, `ptr::copy` and `copy_from_slice` on a raw destination outside `write_out` (positive control: a fixture string with one such call fails it); the Rust services that return output through a caller's slice (GCM and the post-quantum services) assemble it in a module-owned buffer, call the function, then copy. The re-check is immediately before the write; a write already in progress when the state changes completes, so the claim is that no service begins writing output after it has observed the failure. The on-demand test is `oxicrypt_drbg::entropy_on_demand_test() -> Result<SeedPathReport, Error>`: it calls `require_operational()` first, so in any state but `Operational` it returns `NotOperational` and never touches the source; on the assessed path it runs the pipeline's `on_demand_test()` (constructing the pipeline first if none exists) and reports the assessed label; on the operating-system path it performs one 32-byte fill and reports the operating-system label defined above; a failure enters the error state and returns `Error::Rbg(EntropyUnavailable)`. The C form `oxi_entropy_on_demand_test(label_out)` returns `0`, `1`, `32` or `33` and, when `label_out` is not NULL, sets it on `0` and `33` to a static NUL-terminated copy of the label (the cached choice's, or `undecided`); it is how a C program learns the path in use. `oxi selftest` calls it and prints one line in a group `entropy source (1)` placed directly after the `integrity` group, counted in the total, `ok    <label>` or `FAIL  <label>: <error text>` (on `Err` the label is taken from the cached `SeedChoice`, or `undecided` when no instantiate has happened); `--quiet` prints the indicator only. The bench `drbg_first_instantiate` spawns a fresh process per sample (`std::process::Command` on a helper binary) and reports the median and maximum of 20 samples per platform.

**Self-test access to `generate`.** The power-up known-answer tests and the §11.3 health checks run while the module is in `SelfTest`, where `require_operational()` refuses. They reach each type's generate through a crate-internal `generate_internal` (`generate_df_internal` and `generate_no_df_internal` for CTR_DRBG) gated by `oxicrypt_module::require_self_test_started`, the same gate the existing `instantiate_internal` functions and every other `*_internal` function use, with that gate also serving as the output re-check on that path; the public `generate` forms gate on `require_operational()` and `require_operational_for_output()` as stated above. No `*_internal` function is a service, and none appears in the API manifest.

**Gate order.** `instantiate_from_module` and `reseed_from_module` call `require_operational()` and then `require_allowed` with the type's existing DRBG `Service` first (today that gate sits inside `instantiate`, `hmac.rs:251`; it moves ahead of the draw), then check the personalization or additional-input length, then draw. A call before the module is operational returns `NotOperational` and never reaches the entropy source, so a `PowerOff` caller cannot latch the error state through `EntropyError::Module`.

**Instantiate and reseed.** Every DRBG type gains:

```rust
pub fn instantiate_from_module(personalization: &[u8]) -> Result<Self, Error>;
pub fn reseed_from_module(&mut self, additional_input: &[u8]) -> Result<(), Error>;
```

Limits, from the crate's combined-input bounds with the module's seed draw subtracted: personalization at most 720 bytes for HMAC_DRBG and Hash_DRBG (768 combined with 48 bytes of entropy and nonce, `hmac.rs:270`, `hash.rs:225`) and 144 for CTR_DRBG (`MAX_DF_INPUT` 192, `ctr.rs:360`); additional input on reseed at most 736 for HMAC_DRBG (768 minus 32), 680 for Hash_DRBG-SHA-256 and 624 for Hash_DRBG-SHA-384 and -512 (Hash_DRBG's reseed bound counts `1 + SEEDLEN + entropy + additional`, `hash.rs:266`, with SEEDLEN 55 and 111), and 160 for CTR_DRBG. The same bounds apply to `oxi_drbg_generate`'s additional input. Over-length returns `Error::InvalidInput` before any draw. `instantiate_from_module` draws 32 bytes of entropy input and 16 bytes of nonce as two 32-byte requests (the second's unused 16 bytes zeroized), then runs the crate-internal `instantiate_internal(entropy, nonce, personalization)` (`hmac.rs:257`; today's `instantiate` wraps it after its gates), which keeps its length checks and returns `Error` (`InvalidInput`, `EntropyInputTooShort = 29`, `NonceTooShort = 30`, unchanged, so the testing `instantiate` keeps its codes); the profile gate runs before the draw (gate order, below). A failure of the second draw zeroizes the first and returns before any state exists. `reseed_from_module` draws 32 bytes. CTR_DRBG always uses its derivation-function form on this path. An `Error` from `instantiate_internal` is returned as is; a `DrbgError` from the reseed core (`hmac.rs:314`) maps through `rbg_error` into `Error::Rbg`. Re-instantiating is constructing a new value. A `reseed_from_module` that failed on an input check (`InvalidInput`) or on `Busy` leaves the instance unchanged and usable; one that failed on entropy has put the module in the error state, and the instance, like every service, returns `NotOperational` from then on. **Reseeding is automatic:** each DRBG type gains a `module_seeded: bool` field set by `instantiate_from_module`; `fill`, `generate` on a module-seeded instance, `oxi_drbg_generate` and the typed `_generate` call `reseed_from_module(&[])` when `reseed_counter >= HMAC_DRBG_RESEED_INTERVAL` (the existing check is `>`, `hmac.rs:363`; it becomes `>=` on the module-seeded path) before generating, so a module-seeded instance never returns `ReseedRequired`. The automatic reseed calls `require_operational()` and the draw, not `require_allowed` (the instance was admitted at instantiate); its failure surfaces through `generate`'s existing `DrbgError::Module(Error)` variant as `Module(Error::Rbg(EntropyUnavailable))` or `Module(Error::Rbg(Busy))`, which `rbg_error` maps back to the inner variant and `oxicrypt-ffi`'s `From<DrbgError> for OxiResult` (`error.rs:227`) maps through `From<Error>` as it does today. `oxi_drbg_generate`'s additional input is bounded like reseed's per type (`5` over that). Prediction resistance: a consumer that wants fresh entropy before one request calls `reseed_from_module` then `fill`. Request limits are unchanged.

**Testing interfaces.** The caller-entropy forms move behind the default-off cargo feature `testing-interfaces` on `oxicrypt-drbg`: `instantiate`, `reseed`, `generate_pr` on HMAC_DRBG and Hash_DRBG; `instantiate_no_df`, `instantiate_df`, `reseed_no_df`, `reseed_df`, `generate_no_df_pr`, `generate_df_pr` on CTR_DRBG (`generate_no_df` and `generate_df` stay, they take no entropy). The ACVP harness enables the feature; the CAVP DRBG tests supply `entropyInput` and need exactly these forms. The module's own DRBG CASTs are crate-internal and need no feature. **Migration inventory:** the change ships `scripts/list-caller-entropy-sites.sh`, which lists every call to those forms across the workspace (the pattern covers the CTR suffixes), and the change converts each site to `instantiate_from_module`, or, where a test or bench needs a fixed stream, to `oxicrypt_drbg::testing::FixedStream`; to make that possible every function of `oxicrypt-ecdsa`, `oxicrypt-ecdh`, `oxicrypt-rsa`, `oxicrypt-dh` and `oxicrypt-eddsa` that takes `&mut HmacDrbgSha256` today, key generation and signing alike (`p256_ecdsa.rs`, `p384_ecdsa.rs`, `rsa3072.rs` and `rsa4096.rs` among them), becomes generic over `R: Rbg`, which is also what lets them accept any of the nine DRBGs. The script's pattern is `\.(instantiate|reseed|generate_pr|instantiate_no_df|instantiate_df|reseed_no_df|reseed_df|generate_no_df_pr|generate_df_pr)\(` over every `*.rs`, excluding `acvp-harness/`, files under `tests/` whose crate declares `required-features` for them, and `#[cfg(test)]` blocks by brace matching; its output on the merged tree is empty. The one `oxicrypt-entropy` test that drives a DRBG from the pipeline (`pipeline.rs:829`, using the crate-private `PrngMock`) stays in `oxicrypt-entropy` with the dev-dependency on `oxicrypt-drbg` kept and `testing-interfaces` enabled on it (a dev-dependency cycle is permitted by cargo and compiles no shipped code). The seams tests need are one module, `oxicrypt_drbg::seam`, compiled under `cfg(any(test, feature = "fault-injection"))`: `set_get_entropy(fn(&mut [u8]) -> Result<(), RbgError>)` replaces the draw; `draw_count() -> u64`; `construction_count() -> u64` (constructions of `SeedState`, whichever path); `force_seed_choice(SeedChoice)` fixes the path before first use, with `&'static EnvRow` test rows allowed; `force_timer_inadequate(bool)`; `hold_lock() -> SpinGuard<'static, SeedState>` holds the cell from a test thread; `fail_next(FaultClass)` with `enum FaultClass { StartupHealth, ConditionerKat, ContinuousHealth, OnDemand, OsGenerator, SecondDraw }`; `park_before_output(bool)` parks the next service at its output re-check until `release_parked()`; `poison_pipeline()` is `fail_next(StartupHealth)` followed by a draw. Each DRBG type gains `set_reseed_counter(&mut self, u64)` under the same `cfg`. `oxicrypt_platform::testing`, same `cfg`, holds `fork_for_test() -> ForkResult` (Unix only), `set_process_id_override(Option<u64>)`, `set_errno_override(Option<i32>)`, `set_os_random_result(Option<Result<usize, OsRandomError>>)` for the simulated `EINTR`, short return and error, and `SpinCell::with_bound(u32)` for a reduced spin bound under Miri. `fault-injection` is a default-off feature declared in `oxicrypt-platform`, `oxicrypt-drbg`, `oxicrypt-aes`, `oxicrypt-cmac`, `oxicrypt-ml-dsa`, `oxicrypt-ml-kem`, `oxicrypt-ecdh`, `oxicrypt-ecdsa`, `oxicrypt-eddsa`, `oxicrypt-rsa`, `oxicrypt-ffi` and `oxicrypt-cli`, enabled only by test invocations (`cargo test --features fault-injection`) and by the `c-integration` job, which builds the library once with the feature and runs every C case against it (a second, plain build runs the smoke test alone, so the shipped shape is also exercised); it is excluded from release builds by the same per-package rule as `testing-interfaces`, and the same `cargo tree -e features` probe covers both. ### 3. `oxicrypt-platform`, a new in-boundary crate

The module's own calls to the platform, in one small `no_std` crate with the sanctioned `unsafe` category "platform calls: random generator, process id, and the one static cell", listed in the ISA and the Security Policy beside the six existing categories. It depends on `oxicrypt-module` and `oxicrypt-zeroize` (for wiping partial output on failure), declares every symbol in its own `extern` block as `oxicrypt-imageread` does (`lib.rs:302`), and adds no third-party dependency.

### 3a. Built for the environments to come

- Adding an assessed environment is one `EnvRow` plus its Security Policy entry; the build, the C ABI, the Rust API and every consumer are unchanged.
- A new noise source is a `NoiseSource` implementation in `oxicrypt-entropy` (the trait is sealed there and admits new implementations by design), a `SourceKind` variant, a `SeedSource` implementation, and the rows that use it. Nothing above `oxicrypt-drbg` changes.
- Both `SeedSource` implementations compile and are tested on every target through the seam, so flipping a row from the operating-system path to an assessed source is a data change whose behaviour the tests already exercised on that target.
- The on-demand test, the failure semantics and the Security Policy table are per `SourceKind`; a second kind documents itself in the same rows.
- The operating-system path is the floor and is never removed; `oxi selftest` names the path in use.

### 4. Timer features

`oxicrypt-entropy`'s timers are feature-gated and off by default: `raw-counter` enables the CPU counter through `oxicrypt-timer`; `std` enables the operating-system nanosecond clock. `oxicrypt-timer` refuses to compile on any architecture but `x86_64` and `aarch64` (`compile_error!`, `oxicrypt-timer/src/lib.rs:59`), so `oxicrypt-drbg` enables `raw-counter` through a target-specific dependency entry, `[target.'cfg(any(target_arch = "x86_64", target_arch = "aarch64"))'.dependencies]`, and on any other architecture `seed_path()` returns `Os(NoRow)` without constructing a timer. `PlatformTimer::new(RawCounter)` cannot fail where the feature is on (`timer.rs:439`); adequacy is judged in `JitterSource::new`. The `std` timer is not used by the seed path in this change, so no `std` feature is propagated; a future row needing `OsNanoClock` adds the propagation then.

### 5. The C handle, in `oxicrypt-ffi`

```c
typedef struct OxiDrbg OxiDrbg;
int oxi_hmac_drbg_sha256_new_rbg(OxiDrbg **out);   /* _sha384, _sha512 */
int oxi_hash_drbg_sha256_new_rbg(OxiDrbg **out);   /* _sha384, _sha512 */
int oxi_ctr_drbg_aes128_new_rbg(OxiDrbg **out);    /* _aes192, _aes256; derivation function */
int oxi_drbg_instantiate(OxiDrbg *h, const uint8_t *perso, uintptr_t perso_len);
int oxi_drbg_reseed(OxiDrbg *h, const uint8_t *additional, uintptr_t additional_len);
int oxi_drbg_generate(OxiDrbg *h, const uint8_t *additional, uintptr_t additional_len,
                      uint8_t *out, uintptr_t out_len);
int oxi_drbg_strength_bits(const OxiDrbg *h, uint32_t *out);
void oxi_drbg_free(OxiDrbg *h);
int oxi_entropy_on_demand_test(const char **label_out);   /* label_out may be NULL; set to a static NUL-terminated label */
```

The handle is `OxiDrbgHandle { busy: AtomicBool, pid: AtomicU64, inner: UnsafeCell<Option<DrbgKind>> }` in `oxicrypt-ffi` (which already carries `unsafe`), with `enum DrbgKind { HmacSha256(HmacDrbgSha256), /* eight more */ }`; the module writes the kind at construction and every operation dispatches on it with an exhaustive `match`. Every operation but `free` acquires `busy` with a compare-and-swap before any reference into `inner` is formed, releases it through an RAII guard, and returns `Busy = 32` when the swap fails; the reference is formed only inside the guard, so no two mutable references ever coexist. `free` of a handle another thread is using is undefined behaviour and the header says so, as for every handle. `_new_rbg` records `pid = 0`, meaning never instantiated; `instantiate` records `process_id()`. Every operation compares the recorded id before acquiring the busy flag: a recorded 0 skips the comparison (the operation then returns `8` from the DRBG), a mismatch returns `InvalidInput = 5`, so an inherited handle in a child is refused even if the parent's thread held the flag at the fork. `oxi_drbg_instantiate` on an inherited handle is allowed: on a mismatch it clears the busy flag (its holder is a thread of another process) before acquiring it, instantiates, and re-records the id. The header tells a forked child to construct a new handle or re-instantiate the inherited one. `DrbgKind` implements `Rbg` by dispatch, which is how the GCM and post-quantum symbols consume it; those symbols acquire `busy` the same way before use.

**The typed handles.** For each of the nine types: `_new`, `_free` and `_generate` (for CTR, `_generate_df`; `_generate_no_df` is removed with the `no_df` instantiate it belonged to, since every production CTR instance is instantiated through the derivation function) stay; `_instantiate` and `_reseed` (HMAC, Hash) and `_instantiate_no_df`, `_instantiate_df`, `_reseed_no_df`, `_reseed_df` (CTR) are removed; `_instantiate_from_module(handle, perso, perso_len)` and `_reseed_from_module(handle, additional, additional_len)` are added. `OxiHandle<T>` (`handle.rs:24`) gains a `pid: AtomicU64` field, set by `_instantiate_from_module`, so every typed handle carries the record; `_generate` on them, and every consumer that reaches the inner DRBG (ECDH, ECDSA, RSA and DH key generation, `drbg.rs:154`, `lib.rs:2147`), passes through one function, `pub(crate) fn typed_drbg_access<H: TypedDrbg>(h: *mut H) -> Result<&'static mut H::Inner, OxiResult>`, where `pub(crate) trait TypedDrbg { type Inner; fn handle(&mut self) -> &mut OxiHandle<Self::Inner>; }` is implemented by the nine wrapper types (`drbg.rs:139`); it performs, in the shared order, the NULL check (`10`), the process-id check (`5`) and the uninstantiated check (`8`), after the shim's own `require_operational` and `require_allowed`; the nine `inner_mut` methods (`drbg.rs:154` and its eight siblings) are deleted so no consumer can bypass it. The eighteen new typed symbols return the codes of the shared check order; `_instantiate_from_module` on an already-instantiated handle replaces its state and records the current process id; `_reseed_from_module` or `_generate` on a never-instantiated handle returns `8`. They do not gain the busy flag; their header text already requires caller serialisation.

**ABI.** Every merge that removes or changes a C symbol advances `OXI_ABI_VERSION` and records the full inventory as `abi/v<n>.txt` with its `frozen(n)` line count and digest (`abi_tests.rs:41`). This change removes symbols, so it advances the version from 1 to 2 and records `abi/v2.txt`. The AES and post-quantum changes each remove symbols too; whichever merges first advances to 3, the other to 4, each recording its file. Versions are cheap and the ABI test enforces the rule; the release notes name the version shipped.

**Result codes,** appended after `NonceTooShort = 30`: `RbgTooWeak = 31`, `Busy = 32`, `EntropyUnavailable = 33`. (`KeyExhausted = 34` is the AES PRD's.) **Order of checks in every operation on a shared handle, which the AES and post-quantum PRDs adopt by reference:** (1) required pointer NULL → `NullPointer = 10`; optional pointer NULL with non-zero length, length above `isize::MAX`, overlap between an output and any other range → `InvalidInput = 5`; (2) `require_operational` → `NotOperational = 1`; (3) `require_allowed(service)` → `AlgorithmRestricted = 6`; (4) process id → `InvalidInput = 5`; (5) busy → `Busy = 32`; (6) consumer-specific input validity checks (FIPS 203 §7.2 or §7.3 → `InvalidInput = 5`) and then the strength check (→ `RbgTooWeak = 31`); (7) the operation, with the DRBG's own codes (`8`, `12`, `33`; never `9`, since a module-seeded instance reseeds itself) and the operation's. Outputs are written only on success.

## Open risks carried from the entropy source

The Security Policy §9.3.3 records that short timing orbits (period 2 or 3) can evade the RCT and APT continuous tests, and IG D.K Resolution 14 asks that identified failure modes be detected continuously. This change makes the pipeline operational for seeding without changing its tests; the gap belongs to the entropy source's own ISA (`oxicrypt-entropy`, ISC-1 to ISC-28) and is listed here so a reviewer of this change sees it. Its disposition (a periodicity detector in the health layer, or a documented argument that the conditioner's input margin absorbs it) is decided there before the ESV submission, not here.

## Out of scope

- Assessing further operational environments; the table is data and each assessment adds a row.
- Claiming SP 800-90C conformance; noted as not claimed, with the transition date.
- The busy flag on the typed handles; their consumers are unchanged here beyond the process-id check.
- A hardware or jitter source on environments without an assessed claim; those use the operating-system path under Additional Comment 2.
- The GCM and post-quantum services themselves; they are the two PRDs that build on this one.
